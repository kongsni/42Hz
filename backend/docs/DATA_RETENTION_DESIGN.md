## 1. 설계 범위와 현재 사실

현재 Room은 생성 시 24시간 후 expires_at을 설정한다. 비공개 API와 공유 생성에는
만료 검사가 있다. Participant는 Room을 참조하고, Answer는 Room과 Participant를
참조한다. SharedResult는 Room을 필수 참조하며 집계 수치·공유 토큰·생성 시각을
저장한다. 공유 만료·철회·정리·실행 기록은 아직 없다.

근거 파일:

- `backend/src/main/java/com/fortytwohz/room/Participant.java`

V1은 엔티티 기준 로컬 스키마이며 운영 스키마와의 일치를 인증하지 않는다.
기존 21개 테스트의 성공은 이 문서의 수명 관리 기능을 구현·검증했다는 의미가 아니다.

## 2. 확정된 수명 정책

### 2.1 방 개인정보와 원문

- 생성 후 24시간에 방이 만료된다.
- `now >= expires_at`이면 비공개 조회·참여·답변 제출·새 공유 생성·철회를 차단한다.
- 만료 직후부터 삭제 대상으로 선정한다. 추가 24시간을 기다리지 않는다.
- 다음 실행에서 가능한 한 빨리 삭제하며, 만료 후 24시간 이내 삭제가 최종 기한이다.
- 닉네임·참여자 토큰 해시·원문 답변과 방 정보를 정리한다.
- 유효한 공개 요약은 방과의 연결을 해제하고 별도로 유지한다.
- 삭제 후 방 API는 404를 반환할 수 있다. 만료 판정을 위해 Room을 영구 보존하지 않는다.

### 2.2 공개 공유 요약

- `expires_at = 최초 created_at + 7일`이다. 과거 30일 정책을 대체한다.
- 기존 공유에도 최초 생성 기준 7일을 동일 적용한다. 전환 시 이미 7일이 지난 링크는
  즉시 비공개 상태가 되며 삭제 대상이다. 마이그레이션 시점으로 기한을 초기화하지 않는다.
- 반복 공유 요청은 기존 링크·만료일을 반환하며 수명을 연장하지 않는다.
- `now >= expires_at`이면 정리 실행 여부와 관계없이 공개 조회를 차단한다.
- 만료 직후 삭제 대상이며, 만료 후 24시간 이내 물리 삭제한다.
- 방 정리와 공개 요약 정리는 서로 다른 작업·성공 시각·실패 상태로 관리한다.
- 공유 안내 및 공개 화면에 7일 만료 정책을 표시한다.

### 2.3 철회

- 방 만료 전 유효한 참여자라면 누구나 철회할 수 있다.
- 철회와 동시에 공개 요약을 삭제하고 Room에 재공유 금지를 영속 저장한다.
- 어느 참여자도 해당 방의 공유를 다시 생성할 수 없다. 새 방에서만 새 공유가 가능하다.
- 반복 철회는 인증·방 유효성을 확인한 뒤 동일하게 성공한다.
- 철회는 비공개 결과를 삭제하지 않는다. 비공개 조회는 원래 방 만료까지 유지한다.
- 다운로드 이미지, 메시지의 사본, 외부 캐시는 원격 회수할 수 없다. 철회 보장은 서버
  공개 링크에 대한 것이며, 서비스가 제어하는 응답에는 no-store를 적용한다.

### 2.4 운영 기록

- 개인정보 없는 실행 요약·알림 상태 이력은 14일 보관한다.
- 실패 대상 내부 식별자가 꼭 필요한 상세 진단은 최대 3일 보관한다.
- 내부 UUID도 재식별에 쓰일 수 있다. 필요 없는 실패에는 식별자를 저장하지 않는다.
- 대상 삭제 시 해당 진단의 식별자도 같은 트랜잭션에서 제거한다.
- 원문·닉네임·참여자 토큰·토큰 해시·공개 공유 토큰은 기록하지 않는다.
- 현재 미해결 장애 상태와 마지막 전체 성공 시각은 이력 TTL과 별도로 유지한다.
- 로그·백업·외부 서비스의 보관은 별도 통제 대상이다.

## 3. 최소 엔티티·스키마 변경안

### 3.1 Room

- `sharing_blocked boolean NOT NULL DEFAULT false`: 철회 또는 복원으로 재공유를 차단한다.
  기존 status에 섞지 않는다. 체험 진행과 공유 허용은 다른 상태다.
- `retention_review_required boolean NOT NULL DEFAULT false`: 시각 등 이상 데이터의
  접근 차단·수동 확인을 위한 표시. 일반 만료와 구분한다.
- `retention_review_detected_at`: 최초 확인 시각. 정상 행에는 NULL이다.
- created_at/expires_at의 의미는 유지한다. 새 접근 경로도 동일한 검사를 사용한다.

공유 차단은 단방향이다. 일반 API에는 해제 기능을 제공하지 않는다. 방 삭제 시 함께
사라지며, 별도의 영구 철회 원장을 만들지 않는다.

### 3.2 SharedResult

- 기존 집계 수치·share_token·created_at은 유지한다.
- `expires_at`: 정상 데이터는 최초 created_at + 7일. API에서 별도로 검사한다.
- `room_id`: nullable로 변경하며 FK는 Room 삭제 시 SET NULL로 전환한다.
- `retention_review_required`, `retention_review_detected_at`: Room과 동일한 확인 상태.
- 정상 행은 expires_at 필수라는 CHECK를 검토한다. 이상 행은 만료일을 임의 생성하지
  않고 NULL + 확인 필요 상태를 허용한다. JPA 매핑도 이 예외를 명시한다.
- room_id UNIQUE는 유지한다. PostgreSQL의 NULL 허용으로 분리된 요약 여러 개를
  보존할 수 있다. 공개 DTO에는 room_id나 내부 식별자를 추가하지 않는다.

원문을 요약 문자열·JSON으로 복제하지 않는다. 현재처럼 일치/불일치 수치와 승인된
고정 문구로 공개 결과를 구성한다. 완전한 익명성이라고 주장하지 않는다.

### 3.3 최소 운영 테이블 3개

1. `retention_job_state`: 종류별 고정 행. 마지막 전체 성공, 현재 장애/심각도,
   마지막 관측 시각·집계, 관측 유효 여부, 현재 실행 ID, 알림 발송 상태를 보존한다.
2. `retention_event`: 실행 요약과 알림 전환 이력. event_type으로 구분하며 14일 TTL.
   run_id, job_type, 시작/종료, 결과/원인, 시도·삭제·실패·잔여 건수와 관측 시각 등
   비식별 집계만 저장한다. 원본 SQL 오류 메시지·대상별 토큰은 저장하지 않는다.
3. `retention_diagnostic`: 필요한 개별 실패만 보관. run_id, 대상 종류, nullable 내부 UUID,
   제한된 오류 코드, 생성 시각·만료 시각을 저장한다. 최대 3일, 대상 삭제 시 UUID 제거.

실행·알림 전용 큐, Redis, Kafka, 범용 워크플로 엔진은 도입하지 않는다.
알림 이력은 기존 event 테이블에 기록하고 현재 재시도 상태는 job_state에 둔다.

### 3.4 인덱스 후보

- rooms(expires_at): 만료 대상 선택.
- answers(room_id, question_index), participants(room_id): 현재 조회와 방별 삭제 지원.
- shared_results(expires_at): 공개 요약 정리. room_id UNIQUE는 기존 인덱스를 활용한다.
- retention_event(created_at), retention_diagnostic(expires_at),
  retention_diagnostic(target_type, target_id): 기록 만료 및 삭제 후 식별자 제거.

실제 이름·기존 중복 인덱스·테이블 크기·잠금 영향을 확인하고 최종 확정한다.
대규모용 concurrent 인덱스·파티셔닝은 MVP 기본안에 포함하지 않는다.

## 4. Flyway V2 및 V3 이후 분리

1단계 파일: `V2__add_share_lifecycle.sql`. V1과 기존 체크섬은 수정하지 않는다.
V2는 확정 후 수정하지 않으며, 후속 스키마 변경은 V3 이상으로 추가한다.
이번 V2는 아래 1~3 및 정상 공유의 expires_at 필수 CHECK만 포함한다.
4~5의 FK nullable/SET NULL 변경·정리 테이블·인덱스는 V3 이후와 해당 구현 단계에서 진행한다.
현재 SharedResult.room_id는 NOT NULL 및 기존 FK를 유지한다.

구성 순서:
1. Room의 공유 차단·이상 데이터 확인 필드 추가.
2. SharedResult의 만료·확인 필드 추가.
3. 정상 기존 공유에 created_at + 7일을 backfill. 미래 시각·검증 불가능 데이터는
   확인 필요로 분류한다. 판단 기준 시각을 고정하고 경계 기준은 리허설에서 검증한다.
4. shared_results.room_id의 NULL 허용 및 FK 삭제 규칙 변경. CASCADE DELETE는 사용하지 않는다.
5. 운영 기록 테이블과 필요한 인덱스 추가.
6. 정상/확인 필요 데이터의 CHECK 및 무결성 검증.

V2에서 개인정보·공유 요약을 대량 삭제하지 않는다. 접근 차단 코드와 정리 작업이
활성화된 뒤 정해진 서비스 경로로 처리한다. 기존 7일 초과 공유의 서버 접근 차단은
전환 직후부터 적용되도록 배포 순서를 맞춘다.

운영 baseline DB의 FK 이름이 V1 이름과 같다고 가정하지 않는다. 검증된 운영 DDL과
격리 복제본을 기준으로 알려진 FK를 정확히 식별하며, 임의 constraint 일괄 제거는 금지한다.
V2에는 자동 baseline, clean, 유료 undo/diff/generate가 없다.

배포는 스키마 선행 준비와 호환 앱 전환을 조율한다. 구버전 앱은 새 sharing_blocked와
7일 정책을 모르므로, 새 정책을 켠 뒤 구버전 인스턴스가 요청을 처리하지 않도록 한다.
기존 ddl-auto=update 구버전으로 단순 롤백하는 것도 안전한 복구가 아니다.

## 5. 실행 구조

### 5.1 공통 서비스와 진입점

- `RetentionService`: 두 데이터 종류의 대상 선택·처리·집계·결과 기록을 담당한다.
- `RetentionScheduler`: 웹 프로세스가 살아 있을 때 같은 서비스를 호출하는 보조 진입점.
  기본 비활성/설정 기반으로 제공하여 독립 실행과 불필요한 중복을 줄인다.
- `RetentionJobApplication`: 별도 main. 웹 서버를 시작하지 않는 최소 Spring 컨텍스트에서
  같은 서비스를 호출한 뒤 종료한다. 웹 main을 수정해 무조건 배치를 실행하지 않는다.
- 독립 실행은 매시간 수행한다. 웹 서버 가용성과 무관한 별도 실행 환경이 필요하다.
- Flyway는 비활성. JDBC 기반 최소 컨텍스트로 JPA 초기화 자체를 제외하여 Hibernate DDL을
  실행하지 않는다. 실행에 필요한 스키마가 없으면 실패하고 알린다.
- 별도 DB URL/계정은 환경변수 또는 실행 서비스의 secret 저장소에서 공급한다.
  운영/기존 개발 URL로 fallback하지 않는다. 로그/명령행에 비밀번호를 출력하지 않는다.
- 기존 bootJar의 웹 시작 동작을 유지하고, 승인 후 별도 Gradle 실행 task 또는 classifier
  jar로 배치 진입점을 제공한다. DB 변경은 migration 계정의 별도 승인 절차로만 수행한다.

### 5.2 실행 범위와 결과

작업 종류는 ROOM_PRIVATE_DATA, PUBLIC_SHARE를 독립 관리한다.
각각 최대 10분 동안 새 삭제 트랜잭션을 시작할 수 있다. monotonic 시간으로 예산을
판단하고 UTC Instant로 정책 시각을 판단한다. 진행 중 트랜잭션은 안전하게 끝낸다.
작업 시작 시 cutoff를 고정한다. 실행 중 새로 만료된 데이터는 다음 실행 대상이다.

- SUCCESS: cutoff까지의 검사를 완료했고 실패·미처리 대상이 없다. 0건도 포함한다.
- PARTIAL: 일부 대상 실패, 시간 예산 또는 처리량 제한으로 대상이 남는다.
- FAILED: DB 전체 장애, 잠금 연결 상실, 대상 탐색/결과 기록 실패 등 작업 자체의 장애.
- SKIPPED_LOCKED: 같은 종류 작업의 DB 잠금을 얻지 못했다. 성공·실패 어느 쪽도 아니다.
- RUNNING: 아직 완료되지 않은 실행. 프로세스 종료로 남은 상태는 감시가 정체로 판단한다.

정상 실행만 last_full_success_at을 갱신한다. 오류 사유에는 DB_CONNECTIVITY,
LOCK_TIMEOUT, DATA_INTEGRITY, TIME_BUDGET, CAPACITY_LIMIT, LOCK_CONNECTION_LOST,
RESULT_RECORDING_FAILURE 등 제한된 코드를 사용한다. 전체 장애가 있으면 이전에
일부를 삭제했어도 최종 상태는 FAILED이고 삭제 건수는 유지한다.

제안 종료 코드: 0=선택된 모든 작업 SUCCESS, 2=PARTIAL,
3=FAILED, 4=SKIPPED_LOCKED만 포함한 비성공. 여러 결과가 섞이면
FAILED > PARTIAL > SKIPPED_LOCKED > SUCCESS 순으로 집계한다.
외부 실행기는 코드 4를 DB 오류로 오인하지 않고 별도 분류해야 한다.
한 종류 실패가 다른 종류 실행을 생략시키지는 않는다.

### 5.3 잠금 수명과 커넥션

작업 종류마다 고정된 서로 다른 PostgreSQL 세션 advisory lock 키를 사용하고
non-blocking try-lock으로 경합을 판정한다. false와 SQL/연결 예외를 구분한다.
트랜잭션 풀링 주소가 아닌 세션 수명이 유지되는 직접 연결을 사용한다.

MVP에서는 종류별 전용 JDBC 연결 하나를 pin하여 세션 잠금과 짧은 대상별 트랜잭션을
같은 연결에서 수행하는 안을 우선한다. 잠금 연결과 삭제 연결을 분리하면 잠금을 잃은
작업이 다른 연결로 계속 삭제하는 위험이 생기므로 피한다. 같은 세션의 advisory lock은
대상별 commit/rollback 이후에도 작업 종료까지 유지된다.

획득 -> 실행 기록 -> 대상별 transaction 반복 -> 최종 집계/상태 기록 -> unlock -> close.
finally에서 해제하고 닫는다. 공유 풀에 잠긴 연결을 돌려주지 않는다. 연결 상실 시
신규 SQL/대상 처리를 중단한다. DB가 세션 단절을 인지할 때 잠금이 해제되므로 네트워크
단절 시 즉시 해제된다고 단정하지 않는다. socket/query/lock 제한과 외부 2시간 감시를 둔다.
구현에서는 연결 고정·트랜잭션 결합이 실제 동작하는지 통합 테스트로 검증한다.
일반 웹 커넥션 풀의 연결을 반환한 뒤에도 잠금이 남는 구현은 허용하지 않는다.

### 5.4 대상 선택과 트랜잭션

오래된 expires_at, id 순으로 소량을 keyset 조회한다. 삭제 후 offset 페이지를 넘기지
않는다. 실패한 대상 ID는 실행 메모리에만 제외하여 같은 실행에서 재시도하지 않는다.
실행이 끝나면 제외 목록을 버리고 다음 실행에서 다시 선택한다.

방 하나의 transaction:
1. Room SELECT FOR UPDATE, 만료·확인 필요 상태 재확인.
2. 해당 Answer 삭제.
3. 해당 Participant 삭제.
4. SharedResult의 Room 참조 해제(FK SET NULL도 방어선으로 유지).
5. 관련 상세 진단의 대상 식별자 제거, Room 삭제 후 commit.

공유 하나의 transaction:
1. 대상 재조회 및 잠금, 만료 재확인.
2. 관련 진단 식별자 제거, SharedResult 삭제 후 commit.

두 경로의 관련 행 잠금 순서를 일관되게 유지한다. 공유 삭제가 Room을 역순으로
잠그지 않도록 설계한다. bulk JDBC 삭제의 순서와 FK 동작을 실제 PostgreSQL로 검증한다.
중간 오류는 해당 대상 transaction 전체를 rollback하고 나머지를 계속한다.
DB 전체 장애는 반복 SQL을 멈춘다. 재시도는 원칙적으로 다음 매시간 실행에서 한다.

제안 시작값: 조회 배치 50건, 방별 transaction 1개, 쿼리 10초, 잠금 대기 3초.
배치·시간은 설정값이고 운영 지표로 조정한다. SQL 취소 시 DB transaction rollback을
사용하며, 시간 초과를 이유로 불완전한 삭제를 commit하지 않는다.

종료 시 cutoff 이하 잔여 대상을 다시 확인한다. 개별 잠금 경합으로 건너뛴 대상도
잔여에 포함하며, 이를 누락한 채 SUCCESS로 기록하지 않는다.

## 6. 공유 생성·철회·공개 조회

공유 생성과 철회는 기존 Room 쓰기 잠금을 공통 사용한다. 잠금을 얻은 뒤 현재 시각으로
다시 만료/확인 필요 상태를 판정한다. 생성은 sharing_blocked 검사 후 기존 공유를 반환하거나
새 요약을 생성한다. TTL은 생성 시 한 번만 결정한다.

철회 transaction은 참여자 인증 -> Room 상태 검사 -> sharing_blocked=true -> 공유 요약
삭제 -> 관련 진단 식별자 제거 -> commit 순서다. 이미 차단된 방도 유효한 인증이면 동일 성공.
최종 응답의 제안은 204이며, API 클라이언트는 빈 응답을 처리할 수 있도록 최소 수정한다.
조회 API DTO와 기존 비공개 결과는 유지한다.

생성이 먼저 commit되면 뒤이은 철회가 그 결과를 삭제한다. 철회가 먼저 commit되면
이후 생성은 409로 거부한다. 두 transaction이 겹친 사이 이미 완료된 공개 응답까지
회수할 수는 없지만, 철회 완료 후 시작한 조회는 접근할 수 없어야 한다.
기존 공개 조회는 만료 시 410, 물리 삭제/철회 후에는 404로 처리할 수 있다.
서버가 제어하는 공개 API/페이지 캐싱을 막고 철회·만료를 프론트에 안내한다.

## 7. 실패·알림·외부 감시

### 7.1 시간 기준

방 정리와 공개 요약 정리 각각에 적용한다.
- 개별 실행 실패/부분 완료: 확인 즉시 알림.
- 마지막 전체 성공 신호가 2시간 이상 없음: 실행 누락 또는 지속 실패 알림.
- 만료 후 미삭제 12시간: WARNING.
- 20시간: CRITICAL.
- 24시간: OVERDUE 기록 및 즉시 알림.
- 동일 장애/수준은 반복 억제, 상승 또는 복구 시 재알림.

집계에는 대상 수, 최장 만료 경과 시간, 구간별 건수와 observed_at을 포함한다.
실패 대상을 제외한 조회만으로 집계를 만들지 않는다.
상세 진단을 기록할 때는 대상이 여전히 존재하는지 같은 잠금/트랜잭션에서 확인한다.
삭제 후이거나 존재 확인이 불가능하면 대상 식별자를 새로 기록하지 않고 집계 오류만 남긴다. 실행 시작/종료에서 실제 DB를
검사하여 실행 중 삭제된 기한 초과 건수도 해당 실행 요약에 남긴다.

### 7.2 외부 감시는 DB에 접근하지 않는다

확정 선택은 Q2 B다. 외부 감시는 작업별 성공 신호와 마지막 집계만 수신한다.
정리 프로그램이 동작하는 서비스와 별도 스케줄/장애 영역에서 성공 신호의 신선도를
확인한다. 정리 프로그램이 자기 자신의 누락을 판단하는 구조는 사용하지 않는다.

SUCCESS가 아닌 실행 결과는 상태 이벤트로 보낼 수 있지만 성공 heartbeat를 갱신하지
않는다. 검사 대상 0건 SUCCESS도 신호를 보낸다. 신호 전송 실패는 DB 삭제 실패와
구분해 기록하며, 외부에서는 신호 누락을 보수적으로 알린다.

정리 프로그램 중단·관측 실패 동안 마지막 집계를 현재 건수로 표시하지 않는다.
이전 observed_at과 마지막 관측값은 과거 정보로만 보존하고 현재값은 UNKNOWN/측정 불가다.
독립 감시가 즉시 모든 중단을 알 수는 없으므로 화면에는 항상 관측 시각을 표시하고,
다음 보고 지연 시 stale, 2시간 성공 누락 시 장애로 판정한다. 알려진 FAILED도 즉시
현재 측정 불가로 전환한다.

이 기간에 현재 WARNING/CRITICAL/OVERDUE 건수를 추정하거나 0으로 표시하지 않는다.
알려진 이전 장애를 지우지 않고 '관측 불가'를 함께 표시한다. 다음 정상 관측에서
실제 경과 시간·건수를 재계산한다. SUCCESS heartbeat만으로 삭제 지연 경보를 자동
해제하지 않고 신선한 집계가 해소를 증명해야 복구 알림을 보낸다.

첫 운영 활성화 시 종류별 감시를 명시 등록하여 최초 성공 신호가 아예 없는 경우에도
2시간 감시가 동작하게 한다. 외부 감시가 자기 재시작으로 시각을 초기화하면 안 된다.

### 7.3 알림 경로와 전달 실패

기본 채널은 이메일, 메시지는 종류·건수·지연·오류 분류만 사용한다. 대상 UUID·방 코드·
URL·원문 예외·토큰을 포함하지 않는다. 상태 전환별 알림 ID를 사용해 중복을 억제한다.
미전송 상태는 job_state에 남겨 다음 기회에 재시도하며 전송 확인 전 완료 표시하지 않는다.
별도 큐 없이도 전송과 DB 갱신 사이 장애로 중복 메일은 가능하므로 exactly-once를 보장하지
않는다. 최선의 중복 억제와 누락 재시도를 제공한다.

DB가 완전히 불능이면 DB 실패 기록도 쓸 수 없다. 이때 외부 실행 결과/비식별 stderr와
독립 heartbeat 감시가 보완한다. 이메일 제공업체 자체 장애를 이메일만으로 즉시 알리는 데
한계가 있음을 운영 체크리스트에 포함한다.

### 7.4 운영 기록 정리

OPERATIONAL_RECORDS라는 별도 종류로 짧은 정리를 수행한다. 14일 event와 3일 diagnostic을
정리하며 다른 두 작업을 rollback/중단시키지 않는다. 종류별 state는 TTL 대상에서 제외한다.
내부 식별자의 3일 상한은 로그 저장소의 TTL만으로 충족한다고 가정하지 않는다.
정리 주기를 고려한 사전 정리 여유를 두고 상한 초과를 별도 위반으로 감지한다.
이 정리의 결과·마지막 성공도 외부 감시에서 구분할 수 있게 한다. 실패를 기록할 수 없는
상황은 비식별 종료 결과와 신호 누락으로 감지한다. 동일 장애의 무한 로그 생성을 피한다.

## 8. 비정상 데이터

NULL/미래 created_at, 계산할 수 없는 expires_at, 설명되지 않는 생성·만료 관계 등은
자동 보정하거나 기한을 새로 주지 않는다. 정상 시각 데이터와 과거 자료를 구분하는
검증 기준을 구현 테스트와 운영 리허설에서 확정한다.

해당 Room/SharedResult는 review_required로 접근·공유를 차단하고 자동 삭제에서
일시 제외한다. 제외 건수는 별도 보고하여 SUCCESS/잔여 집계에서 숨기지 않는다.
경로가 blocked인 것을 정상 정리 완료로 오인하지 않는다.

발견 즉시 운영자에게 알리고, 제한된 내부 화면/조회 절차로 최소 정보를 확인한다.
원본 정의·백업·생성 경로를 대조하여 '근거 있는 시각 복구' 또는 '별도 승인 삭제'로
종결한다. 오염된 데이터를 무기한 두는 자동 예외는 허용하지 않는다. 미해결 현황과
담당/조치 상태를 추적하고 최소 매일 확인한다. 이 일일 확인은 보관 기한 연장이 아니다.
기한을 산정할 수 없으면 삭제 준수 여부도 측정 불가로 표시한다.
운영 전환 전에 발견한 이상 데이터는 해소 전 배포 승인 조건을 충족하지 못한다.

## 9. 백업과 복원

### 9.1 백업 보관

개인정보를 포함하는 백업 최대 보관은 7일을 목표로 한다. 서비스 DB의 즉시 접근 차단·
24시간 삭제와 백업의 보관을 구분해서 안내한다. 접근 최소화·암호화·만료 폐기·복원 기록을
관리하며, 수동 다운로드/추가 사본도 포함한다. 외부 로그의 TTL은 별도로 확인한다.

Neon 등 실제 제공업체의 복구 이력·스냅샷·삭제·키 관리 지원을 확인해야 한다.
7일 상한을 지원하지 않거나 별도 사본이 더 오래 남는다면 운영 적용 전에 보고하고
재검토한다. 현재 제공업체 설정을 변경하거나 백업 생성·다운로드를 실행하지 않는다.

### 9.2 복원 절차와 공유 무효화

1. DB 복원 전 외부 접근·신규 방 생성·자동 정리 실행을 외부에서 차단한다.
   복원될 DB 안의 플래그만으로 접근 차단을 구현하지 않는다.
2. 새 격리 환경에 복원하고 실제 schema/history/백업 시점을 확인한다.
3. 해당 시점 마이그레이션 파일·checksum을 검증하고 필요한 forward migration을 검토·적용한다.
   이미 이력이 있으면 다시 baseline하지 않는다. Flyway 이전 백업이면 별도 onboarding이 필요하다.
4. 모든 복원 Room에 sharing_blocked=true를 저장하고, 복원된 모든 공유 요약을 무효화/삭제한다.
5. 원래 created_at/expires_at으로 만료 원문을 우선 정리한다. 운영 기록의 복원된 대상 식별자도
   함께 정리한다. 시간을 복원 시점 기준으로 재설정하지 않는다.
6. 기한 지난 운영 기록, 잘못된 데이터, FK/UNIQUE와 API 경계를 검증한다.
7. 복원된 오래된 실행 상태를 현재 성공 신호로 발송하지 않는다. 복원 환경에서 실제 검사 후
   새 성공을 기록하고 외부 감시도 복구 상태를 확인한다.
8. 모든 검증 후 외부 접근·실행을 재개한다. 실패 시 계속 차단하고 알린다.

기존 공유는 잔여 TTL과 무관하게 영구 무효다. 복원 Room에서 새 공유도 금지하며,
복원 후 생성된 새 Room만 공유 가능하다. MVP에는 외부 철회 원장이 없다.

### 9.3 복원 Room과 새 Room의 구분

created_at과 '복원 시각'을 비교하지 않는다. 시계 오차·미래 시각·반복 복원·작업 중단에
취약하기 때문이다. 접근/생성이 차단된 시점에 존재하는 모든 Room에 직접 block을 기록한다.
복원 완료 후 새로 생성되는 Room만 기본 false다. 추가 세대 테이블은 필요 없다.

복원 절차에는 고유 restore_run_id와 차단/스키마확인/무효화/정리/검증/완료 체크포인트를 둔다.
DB 외부의 승인된 복구 기록에 진행 상태를 남겨 DB 복원으로 gate가 초기화되지 않게 한다.
같은 실행을 중단 지점에서 반복해도 block 해제나 공유 복구를 하지 않는다. 완료한 절차를
온라인에서 다시 수행하지 못하도록 대상 DB·작업 ID·외부 차단 상태를 확인한다.
새 방이 생긴 정상 운영에서 전체 Room block을 다시 실행하는 것을 금지한다.
정상 운영의 공유에는 복원 전용 처리 경로를 적용하지 않는다.

### 9.4 서비스 재개 조건

- 모든 복원 공유 조회 차단 및 복원 Room 재공유 차단 확인.
- 원래 기한이 지난 개인정보/원문 제거, 진단의 연관 식별자 제거 확인.
- 비정상 데이터 확인 완료 및 무결성·Flyway·JPA 검증 통과.
- 새 방의 정상 API·공유, 복원 Room의 차단 통합 검증 통과.
- 실행기·외부 감시의 현재 검사/전달 정상화, 운영자 재개 승인.

## 10. 보안과 개인정보 보호

- migration 계정과 배치 계정 분리. 배치는 DDL/테이블 소유 권한 없이 필요한
  SELECT/DELETE, 공유 참조 해제 UPDATE 및 운영 기록 INSERT/UPDATE만 요청한다.
- MVP 외부 감시는 DB 자격증명을 받지 않는다. 실제 역할 분리는 운영 승인 단계다.
- schema를 제한하고, token·answer·nickname 컬럼을 불필요하게 읽지 않는 SQL을 사용한다.
- 공유 토큰은 공개 링크 자체에서만 사용하고 진단·이메일·프로세스 인수에 기록하지 않는다.
- SQL 예외의 '실패 행' 상세에도 개인정보가 포함될 수 있으므로 raw exception/바인딩 로그를
  수집하지 않는다. 허용된 오류 코드와 최소 스택 위치만 사용한다.
- 정리 완료와 진단 식별자 제거를 동일 transaction으로 묶는다. 다른 동시 실행이 삭제 후
  식별자를 다시 기록하지 않도록 종류별 잠금·대상 존재 확인·잠금 순서를 검증한다.
- 복구용 backup, 외부 로그, 이메일의 TTL은 별도다. 이메일 내용은 처음부터 비식별로 한다.

## 11. 테스트 계획

기존 개발·운영 DB를 사용하지 않고 Testcontainers PostgreSQL로 실행한다. 실제 시간 대기
대신 주입한 Clock을 사용하며, 종료 예산은 별도 monotonic 시간 공급으로 테스트한다.

필수 시나리오:
1. 방 24시간/공유 7일 직전·정각·직후 API 경계.
2. 만료 직후 삭제 대상, 방 삭제 후 유효 공유 유지·room_id NULL.
3. 닉네임/토큰 해시/답변/방 삭제와 진단 식별자 제거.
4. 기존 공유의 created_at 기준 7일 적용, 반복 공유의 expires_at 불변.
5. 양쪽 참여자 철회, 반복 철회, 다른 참여자의 재공유 거부.
6. 공유 생성-철회 경합의 두 commit 순서와 공개 조회 차단.
7. 삭제 중 예외의 전체 rollback, 다른 대상 commit 유지, 다음 실행 재시도.
8. 실패 대상 재선정 방지와 다음 실행의 제외 목록 초기화.
9. 종류별 session lock 경합, 연결/프로세스 종료, 동일 pin 연결의 transaction 경계.
10. 10분 신규 처리 예산과 진행 중 transaction 종료, 시간/용량/DB 원인 구분.
11. SUCCESS/PARTIAL/FAILED/SKIPPED_LOCKED/대상 0건과 last_success 갱신 규칙.
12. 12/20/24시간 실측 집계, 실패/누락 2시간 감시, 중복 억제·복구·이메일 재시도.
13. 보고가 멈추면 측정 불가, 오래된 수치나 0건을 현재값으로 표시하지 않음.
14. event 14일/diagnostic 3일 경계, state 보존, 기록 정리 실패 독립 감시.
15. 비정상 시각 접근 차단·분류·해소 절차와 잔여 건수 포함.
16. 복원 시 모든 기존 공유 무효화/모든 복원 Room block, 중단·재실행 멱등성,
    새 방만 공유 가능, 정상 운영에는 복원 처리 미적용.
17. V1 -> V2에서 기존 PK/답변/공유 토큰·최초 생성 시각 보존 및 7일 backfill 검증.
    FK SET NULL와 nullable 매핑 검증은 V3 이후 해당 변경 단계에서 수행.
18. 기존 연인 모드 2인 13질문·비공개 결과·공개 요약 API 회귀 검증.
19. 알림·로그·진단에 금지 데이터가 없는지 자동 검사, 권한 최소화 리허설.

V2 테스트에 운영 FK 이름과 다른 Hibernate 생성 이름의 baseline 스키마도 포함한다.
의도한 실패 주입은 검증된 rollback을 요구하며 테스트 자체의 실패를 무시/skip하지 않는다.

## 12. 실행/감시 서비스 선정 원칙

정책은 확정됐지만 공급자는 아직 선정하지 않았다. 모든 정책 결정 후 무료 우선,
부족하면 실행·감시·이메일 합계 월 US$5 이내 후보를 비교한다. 결제는 별도 승인이다.

비교 항목은 시간 단위 실행 지연/누락, Docker/Java 지원, secret 관리, direct PostgreSQL
연결, 독립 heartbeat 감시, 종류별 상태·이메일·중복 억제, 무료 제한/초과 비용,
계정 정지 시 동작, 지역/데이터 취급, 로그 TTL이다. 단순 정기 ping으로 Render를
항상 깨우는 방식은 독립 실행의 대체가 아니다.

Render Free 내부 스케줄러는 유휴/재시작/사용량 중단으로 기한을 단독 보장하지 못한다.
무료 외부 실행·감시 역시 장애와 지연이 있다. '24시간 이내' 정책 이행을 위해 관측·
복구 책임이 필요하며 어떤 무료 구성도 무조건적인 무중단 보장으로 설명하지 않는다.
외부 감시가 정리 실행과 같은 프로세스/동일 스케줄에 종속되지 않는지 확인한다.

## 14. 단계별 구현 순서

1. **별도 구현 승인**: 이 문서 검토 후 코드/로컬 DB 테스트 범위를 승인받는다.
2. **Clock와 공유 정책**: Room block, 7일 계산·조회 차단·철회·경합 테스트를 준비한다.
3. **V2 로컬 리허설**: 빈 DB 및 V1/legacy baseline 데이터에 V2 적용·보존·무결성 검증.
4. **V3 이후 스키마 및 삭제 서비스**: 순서·짧은 transaction·참조 해제·멱등성·개별/전체 실패 검증.
5. **실행기**: pin 세션 잠금, cutoff, 예산·배치·종료 코드, Spring 보조 scheduler.
6. **기록/감시 계약**: 종류별 state/event/진단 TTL, 집계 신선도, 전송 재시도·알림 억제.
7. **프론트**: 철회·7일 안내·비공개 결과 유지·만료 UX 확인.
8. **복구 리허설**: 별도 복원 프로그램/절차의 gate·block·정리·재개 조건 통합 검증.
9. **서비스 비교만 수행**: 무료/월 $5 후보와 backup 7일 지원 여부를 보고한다.
10. **운영 사전 검증 및 별도 승인**: 계정 연결·role·V2·기동/작업 배포·활성화는 이후다.

위 순서는 리뷰 단위다. V2가 필요한 새 코드를 기존 스키마에서 먼저 실행하지 않는다.
각 단계의 최종 상태에 맞는 격리 schema를 사용하며 통과한 테스트만 근거로 다음 단계로 간다.

## 15. MVP 필수와 추후 고도화

MVP 필수:
- 모든 방/공유 기한, 소급 7일, 철회·재공유 차단, 참조 해제·삭제.
- 독립 실행기와 보조 scheduler, DB 잠금, 짧은 transaction, 실패 재선정/예산 처리.
- 영속 결과·성공 시각, 기록 TTL, 별도 heartbeat 감시와 이메일, 측정 불가 표시.
- 비정상 데이터 조치 절차, 최소 권한/비밀 관리, 복원 gate와 공유 전면 무효화.
- 격리 PostgreSQL 검증 및 운영 전환/백업 리허설.

추후 고도화:
- 추가 알림 채널, 전용 메시지 큐/outbox, 더 강한 알림 전달 보장.
- 대규모 병렬 정리·분산 fencing·파티셔닝·concurrent index 등 처리량 개선.
- 외부 감시의 읽기 전용 DB 집계 권한(현재 미채택), 실시간 운영 대시보드.
- 정상 공유를 살리는 외부 철회 원장/선택적 복구(현재 MVP 미채택).
- 모드/분석 버전 도입 및 그에 맞는 요약 snapshot 확장. 원문 비보관 원칙은 유지.

## 16. 운영 배포 전 필수 검증과 남은 위험

- 전체 운영 DDL/FK 이름·타입·시간 정밀도·기존 데이터 이상 여부 확인.
- 운영 V1 baseline 완료 여부와 checksum 확인. V2 및 후속 migration 대상/잠금 시간/되돌림 대책 검토.
- 현재 기본 Hibernate validate가 기존 DB를 거부할 수 있으므로 복제본 기동 검증.
- 구버전 인스턴스의 update·7일 미적용·차단 무시 경로 제거.
- 독립 실행/외부 감시/이메일의 계정·권한·비용·누락 테스트, 실제 초기 신호 확인.
- 운영 활성화 전 미삭제 backlog와 7일 초과 공유의 처리 계획·공지 확인.
- backup 최대 7일, 암호화·접근·폐기 및 전체 복원 리허설의 실제 지원 여부 확인.
- raw SQL 예외·access log URL·외부 APM/로그에도 식별자가 남는지 별도 확인.
- 외부 감시에 DB 접근을 주지 않는 MVP 결정상 중단 중 실제 미삭제 수치는 UNKNOWN이다.
  12/20/24시간 경보를 실측할 수 없다는 점을 성공 신호 누락 경보로 숨기지 않는다.
- 이상 데이터는 자동 보관 연장이 아니며 해결 전 수명 정책 준수를 주장할 수 없다.
- 10분은 시작 예산이다. 실제 종료 지연, 네트워크 단절의 session lock 해제 지연,
  backlog 증가, 이메일 중복/누락, 외부 캐시 잔존은 테스트/운영 감시 대상이다.
- backup/로그 TTL이 정책과 다르면 운영 적용 전에 보고·재승인한다.

현재 결론: 이 문서는 구현 기준이다. 1단계 V2는 공유 수명 정책만 담당하며, 정리·감시 등 전체 기능 완성 전 운영 배포·정책
준수 상태가 검증된 것은 아니다. 기능 구현/DB 변경/외부 연결/commit/push/deploy는 별도 승인한다.
